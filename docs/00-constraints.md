# Ограничения проекта (жёсткие)

Документ фиксирует правила, которые нельзя нарушать без явного решения владельца.
Действует для всего репозитория `gergram/` и всего форка Telegram для macOS.

## 1. GitHub — только персональный аккаунт

**Правило:** все репозитории, issue, PR и push — только под аккаунтом **`geranton93`**.
Корпоративный аккаунт `antonh-ai-districtcyber` не используется **ни в чём**.

### 1.1 Почему это важно (риск по умолчанию)

Проверено на машине:

| Канал | Кто авторизуется по умолчанию | Риск |
|---|---|---|
| `gh` CLI (активный аккаунт) | `antonh-ai-districtcyber` — **корпоративный** | любой `gh`/`git push` уходит в корпоративный аккаунт |
| SSH `git@github.com` | `antonh-ai-districtcyber` — **корпоративный** | пуш по ssh тоже корпоративный |
| SSH-ключ `~/.ssh/id_github_personal` | `geranton93` — **нужен нам** | ключ есть и работает |
| `~/.ssh/config` | алиас `github.com-districtcyber` → корпоративный | глобальный `github.com` не переопределён |

### 1.2 Что уже сделано (project-scoped, без правок глобальных настроек)

В `.git/config` этого репозитория:

```ini
[user]
	name = geranton93
	email = Xlive93@yandex.ru
[credential "https://github.com"]
	username = geranton93
[core]
	sshCommand = ssh -i ~/.ssh/id_github_personal -o IdentitiesOnly=yes
```

`core.sshCommand` гарантирует, что любой `git push` из этого репозитория аутентифицируется
персональным ключом, даже при глобальном `Host github.com` → корпоративный.

### 1.3 Правило для CLI

`gh` использует активный аккаунт (корпоративный). Для любой gh-команды в этом проекте:

```bash
GH_TOKEN="$(gh auth token --user geranton93)" gh <команда>
```

Проверено: `GH_TOKEN=... gh api user --jq .login` → `geranton93`.

**Запрещено:** `gh auth switch --user antonh-ai-districtcyber`, любые операции от имени
корпоративного аккаунта, добавление корпоративных ремотов.

## 2. GPL-2.0 — условия законного форка

Swift-клиент Telegram распространяется под **GPL-2.0** (старый Objective-C клиент был
proprietary — это не про него). Форк и публичная раздача разрешены при соблюдении
условий из README апстрима:

1. **собственный API ID** (получить на `core.telegram.org/api/obtaining_api_id`);
2. **не называть продукт «Telegram»** и не создавать впечатления, что это официальный клиент;
3. **не использовать стандартный логотип** (белый бумажный самолётик в синем круге);
4. **соблюдать гайдлайны безопасности** `core.telegram.org/mtproto/security_guidelines`;
5. **публиковать исходный код** — этого требует сама GPL.

Следствия для проекта:
- наш форк тоже распространяется под GPL-2.0;
- бренд и иконки — свои, `bundle id` — свой, `Team ID` — свой;
- в `packages/ApiCredentials/Sources/ApiCredentials/Config.swift` подставляются свои
  `apiId`/`apiHash`, `bundleId`, `Team ID`, свой App Group;
- `SFEED_URL` в `configurations/*.xcconfig` заменяется на свой (или Sparkle отключается).

## 3. Апстрим — только для чтения

| Репозиторий | Роль | Как используем |
|---|---|---|
| `TelegramOrg/Telegram-macos-Swift` | официальное зеркало, только ветка `master` | upstream для merge, сверка |
| `overtake/TelegramSwift` | корень проекта, ветки `master`/`release`/`appstore` | источник релизных обновлений (его же предписывает `INSTALL.md` апстрима) |
| `overtake/Telegram-iOS` | ядро (MTProto, Postbox, account manager) | свой форк `geranton93/gergram-ios-core` |
| `AyuGram/AyuGramDesktop` | источник функциональных требований | только чтение, референс поведения |

Правила:
- апстримные репозитории **никогда** не получают push;
- форк нашего кода лежит только в `geranton93/gergram-macos`;
- merge апстрима — отдельная операция с проверкой конфликтов (см. `docs/02-macos-swift-analysis.md`, §6.4).

## 4. Инженерные правила форка

1. **Наши правки — изолированными файлами/пакетами** (`packages/Gergram*`), а не размазанными
   изменениями по апстримным файлам: `ChatRowItem.swift` (3978 строк), `ChatController.swift`
   (~10 000), `AccountContext.swift` (986) — основные точки конфликтов при merge.
2. **Правки ядра — минимальными и в отдельных файлах**: `Telegram-iOS` обновляется ежедневно.
3. **Никаких комментариев в коде** — правило владельца проекта (self-documenting code).
4. **Каждая фича — отдельный тикет** с вертикальным срезом и явными блокирующими связями.
5. **Проверка = сборка + ручной сценарий**: unit-тестов в `Telegram-Mac/` нет,
   тестовая инфраструктура — наш долг, а не апстрима.
